# Device Manager 后续功能候选

本清单用于下一轮范围选择，以下功能尚未实现。当前系统已有 OTA 发布与 A/B 恢复、升级审计、设备上报和只读 SOL；“近五分钟上报”不能证明设备持续在线。OpenBMC 的 [Web UI 设计](https://github.com/openbmc/docs/blob/master/development/web-ui.md) 和 [bmcweb](https://github.com/openbmc/bmcweb) 可作为管理信息模型参考，但本项目需要按现有板卡和代理能力独立取舍。

| 优先级 | 候选功能 | 解决的问题 | 实现前提或边界 |
| --- | --- | --- | --- |
| 高 | 设备心跳、硬件清单与健康状态 | 区分在线、离线和只在某次升级中出现过的设备；查看 SoC、内存、存储、网卡与固件槽位 | 定义设备 ID 和心跳过期规则；避免把 SOL 连接当成健康状态 |
| 高 | TLS、身份认证与权限分级 | 调试模式免凭据只适用于受控网络；生产环境需限制上传、发布、查看日志和恢复操作 | 证书轮换、设备身份、操作者审计；先明确部署环境与信任根 |
| 高 | 日志与故障归档 | 将 panic、pstore、服务崩溃及启动失败与具体固件 ID、设备和时间关联 | 先完成设备 `/data` 持久化验收；限制上传体积和保留时间 |
| 中 | 分组灰度发布与暂停 | 从单一当前发布扩展到按产品、设备组和批次投放；异常时自动停止后续批次 | 明确目标选择、成功阈值、超时与人工解除规则；保留现有异常停发机制 |
| 中 | 监控与告警 | 汇总 CPU、内存、温度、存储寿命、网络错误和 watchdog 事件 | 采样频率、离线缓存、阈值与告警去重；仅采集板卡实际支持的指标 |
| 中 | 远程诊断任务 | 在无 SSH 环境中采集 `perf`、`ftrace`、网络统计等定位材料 | 任务白名单、资源上限、超时和结果脱敏；与 SadBoard 场景引擎保持独立接口 |
| 中 | 固件来源和签名 | 从内容哈希扩展到构建来源、签名校验及可追溯物料清单 | 签名密钥管理、SPL/U-Boot 信任链和恢复镜像策略；SHA256 本身不证明来源可信 |
| 中 | 远程配置与备份 | 管理网络参数、日志策略和服务配置，支持回退 | 配置模式、密钥隔离、变更审计和设备重启策略 |
| 后续 | 启动前网络救援 | eMMC/SD 的内核或 rootfs 严重损坏时主动请求服务器恢复 | 需验证 U-Boot 网络驱动、下载完整性、可信引导与断电恢复；不应依赖正常 Linux 启动 |
| 后续 | 电源和外设管理整合 | 从统一页面查看或控制受支持的板卡电源/外设状态 | 通过 EDK/libbmc 的明确 API 接入；Device Manager 不复制外设管理逻辑 |

## 建议的下一步

先选“设备心跳与清单”或“故障归档”做端到端方案和板卡验证：两者能改善当前页面的状态可信度与问题溯源。若准备接入非受控网络，应先决定 TLS 与设备/操作者身份模型。灰度发布、远程诊断和启动前救援需要单独确定风险边界，再设计协议和验收条件。
